# SolarSphere AI — Feature 3: AI Government Solar Planning

Feature 3 takes rooftop-level solar assessment results generated by Feature 1 for multiple
locations, aggregates them geographically, calculates locality and city-level solar
potential, visualizes it through GIS, and provides budget-based planning scenarios,
environmental impact, and an AI-assisted government planning report.

There is **no Building_ID** anywhere in this feature. The geographic identity of a record is
`Location_Input + Latitude + Longitude + Locality + selected rooftop`.

---

## 1. Pipeline

```
FEATURE 1 EXCEL OUTPUT
        ↓
Data Ingestion → Data Validation → Data Cleaning
        ↓
Geographic Grouping → Locality Aggregation → Solar Potential Index
        ↓
GIS Visualization → Government Dashboard → Budget / What-If Simulation
        ↓
Scenario Comparison → Environmental Impact → AI Planning Assistant (RAG)
        ↓
Solar Planning Report (PDF)
```

## 4. Setup

### 4.1 Database

```powershell
# PostgreSQL 16 service must be running
$env:PGPASSWORD='postgres'
psql -U postgres -h localhost -c "CREATE DATABASE solarsphere;"
```

Default connection string (override with `DATABASE_URL`):

```
postgresql+psycopg2://postgres:postgres@localhost:5432/solarsphere
```

### 4.2 Backend

```powershell
cd backend
pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

On first start the bundled Feature 1 workbook in `data/` is loaded automatically
(120 valid rooftop records, 8 localities, 0 issues).

Optional LLM rephrasing layer for the assistant (numbers are always computed locally):

```powershell
$env:OPENAI_API_KEY = "sk-..."
# optional: $env:LLM_BASE_URL, $env:LLM_MODEL
```

### 4.3 Frontend

```powershell
cd frontend
npm install
npm run dev          # http://127.0.0.1:5173
```

Production build: `npm run build` (type-checks with `tsc -b`), lint: `npm run lint`.

## 7. Solar Potential Index (project decision-support score, 0–100)

| Factor | Default weight | Direction |
|---|---|---|
| Usable rooftop area | 25 | higher better |
| Generation potential | 25 | higher better |
| Capacity potential | 20 | higher better |
| Economic feasibility (annual savings) | 15 | higher better |
| Payback feasibility | 10 | **lower payback scores higher** |
| Suitability (High/Med/Low = 1.0/0.5/0.1) | 5 | higher better |

Numeric factors are min-max normalized across the uploaded dataset, multiplied by the
(weights rescaled to 100), summed. A locality index is the mean of its rooftop indices.
The breakdown is shown point-by-point in the UI, so every score is explainable.
This is **not** an official government score.

## 8. Data classification (shown in UI, report and docs)

- **A — Feature 1 output**: read from the Excel.
- **B — Calculated by Feature 3**: aggregates, index, CO₂, distributions.
- **C — Real public data**: OpenStreetMap basemap.
- **D — Simulated / demo**: `SYNTHETIC_DEMO` source rows and budget scenarios.
- **E — User-configured assumption**: emission factor, index weights, budget, thresholds.

## 9. Replacing the demo dataset with real Feature 1 outputs

The uploaded workbook is the single source of Feature 1 values. Drop the real export on
**Data Management → Excel data upload**; the importer maps columns by normalized name
(`Estimated_Installation_Cost_INR` → `installation_cost_inr`, …), validates coordinates and
numeric ranges, detects duplicates, groups by `Locality`, and rebuilds every aggregate,
index, map layer and chart. No architecture change is required.

## 10. Limitations

- Demo rows are synthetic (`Data_Type = SYNTHETIC_DEMO`); magnitudes are illustrative until replaced with real Feature 1 outputs.
- The Solar Potential Index is a project aid, not a statutory rating.
- Budget scenarios are simulations: no approval, award or shortlisting is implied.
- CO₂ figures are indicative planning estimates, not verified carbon credits.
